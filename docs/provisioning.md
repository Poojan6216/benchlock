# Provisioning: how big does the anchor set need to be?

> **Design law.** The anchor process must be provisioned to reach its threshold no later
> than the system process would, for any judge shift large enough to move the system stream
> detectably.

If it is not, a judge shift moves the system stream past its threshold before the anchor
stream can prove it, and the obvious reading — "the system moved and the judge didn't" — is
exactly wrong. The team rolls back a healthy release.

`benchlock plan` enforces the law at design time. Lattice rule 6 enforces it at run time by
returning `indeterminate` instead of `system` whenever the anchor set lacked the power.

## The short version

```sh
benchlock baseline --anchors your-suite.jsonl   # measures the judge's noise floor
benchlock plan --target-shift 0.05              # tells you how many anchors you need
```

`plan` refuses to run before `baseline`, because provisioning depends on how much your
judge disagrees with itself, and that has to be **measured rather than assumed**.

## How anchor size actually buys precision

Not as `1/sqrt(n)`. A judge's run-to-run variation has two parts:

```
run_mean_sd² = shared_sd² + per_item_sd² / n
```

- **`per_item_sd`** — independent wobble on each item. This *does* shrink as the anchor set
  grows.
- **`shared_sd`** — a run-level offset that moves every item together: a provider-side
  change, a different sampling kernel, a load-shedding fallback. This **does not shrink at
  all.**

Where the shared component alone exceeds your target, no anchor size is sufficient, and
`benchlock plan` says so rather than returning a large number that would not have worked:

```
error: no anchor size can detect a judge shift of 0.02 within 50 runs at alpha=0.05.
       The judge's shared run-to-run noise is 0.0200, which moves every anchor item
       together and so does not shrink as the anchor set grows
  fix: raise --target-shift, lengthen --horizon, increase `anchor.noise_replicates` so the
       snapshot is measured more precisely, or reduce the judge's own variability
```

`plan` also reports **marginal gain at 4×**: how much the detectable shift improves if you
quadruple the anchor set. Below 10%, buying more anchors is wasted money and it says so.

## The dead zone

The frozen baseline is itself one measurement of a noisy judge, so it sits an offset away
from the judge's true mean. That offset is bounded by a Student-t interval on `K-1` degrees
of freedom:

```
dead_zone = t(K-1, α_b/2) · run_mean_sd / sqrt(K)
```

**A shift smaller than the dead zone can never be detected, however long you watch.** More
replicates shrink it; more anchor items do not. `plan` prints it.

With `K=2` the t-quantile on 1 degree of freedom is enormous and the null covers everything,
so nothing can ever be rejected. That is the honest answer to "I took two measurements", not
a bug. `K=5` is the default for a reason.

## Worked example

A judge with per-item self-disagreement of 0.08, K=5 replicates, a 50-run horizon, and **40**
items per system run (the smaller system stream is what lets the detectability leg, rather
than the design-law leg, decide the size):

| target shift | anchor n | what limits it |
|---|---:|---|
| 0.10 | 40 | the design law against the system stream |
| 0.05 | 40 | the design law |
| 0.03 | 96 | detectability |
| 0.02 | 215 | detectability |
| 0.015 | 382 | detectability |
| 0.01 | 858 | detectability |

Generated by `min_anchor_size` with the noise floor above; reproduce with
`benchlock plan --target-shift <t>` against your own measured floor.

## Why the formula is what it is

The detection time comes from the rate at which a betting process accumulates log-wealth.
The obvious model is the quadratic KL rate, `δ² / 2σ²`, and **it is wrong here**: the
growth-optimal bet is above its truncation in every realistic regime, so growth is *linear*
in the drift rather than quadratic. Using the quadratic rate made the calculator claim
shifts were detectable that simulation never detected at all.

The formula is solved numerically against the truncated bet, with a safety factor
calibrated against simulation. At the recommended size the target shift is detected 100% of
the time across six configurations, against the 95% the design law requires — see
`bench/results/provisioning-calibration.json`.

Every rounding goes the conservative way: sizes round up, detectable shifts round up, and
the search returns the larger `n` when ambiguous. Under-provisioning produces confidently
wrong verdicts; over-provisioning costs judge tokens.
